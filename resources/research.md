# AI detection research for X AI Signal

Last reviewed: 2026-07-05.

## Product decision

X AI Signal should estimate whether an account's observed activity looks automated, repetitive,
or low-value. It should not claim that a post was written by AI or that an account is a bot.
Those claims cannot be made reliably from ordinary short posts.

The useful unit is not one post. It is an account record that improves as the user encounters
more of that account. A first post may provide only weak content evidence. Later posts can reveal
repetition, timing, reply patterns, and shared links. A profile card opened by the user can add
account context. The extension then combines the available evidence and states how much it has
seen.

This requires two separate outputs:

- **Suspicion**: how strongly the observed evidence suggests repetitive or automated behavior.
- **Coverage**: how much independent evidence supports that judgment.

Seeing more posts must not increase suspicion by itself. It increases coverage and may move the
suspicion score up or down. A high score from one short post remains `unknown`; a low score after
twenty varied posts can be shown as low suspicion with meaningful coverage.

The current deterministic text scorer is a UI baseline, not an AI detector.

## What can and cannot be detected

"AI account" mixes several different questions:

| Question | Locally observable? | Product use |
| --- | --- | --- |
| Was this exact text generated by a model? | Rarely; short-text detectors are unreliable | Weak evidence only |
| Was AI used to edit or translate it? | Usually not | Do not guess |
| Does this account behave automatically? | Partly, after repeated observations | Main scoring target |
| Is this reply repetitive or low-value? | Often, with conversation and user context | Main product target |

A person can post templated spam. A model-assisted post can be useful. The indicator should
therefore describe observed behavior, not moralize about tools or authorship.

## Research that affects the algorithm

### Text classifiers are weak on X-length content

Text detectors use style rules, supervised classifiers, or token probabilities from language
models. All can work on data similar to their training set and fail on a new generator, topic,
language, editing style, or text length.

OpenAI withdrew its classifier after reporting 26% detection of AI text and 9% false positives;
it also described text below 1,000 characters as very unreliable. Most X posts are far shorter.
See [OpenAI's archived classifier page](https://openai.com/index/new-ai-classifier-for-indicating-ai-written-text/).
Tweet-specific research reports the same short-text problem. The
[short-form synthetic text study](https://aclanthology.org/2024.lrec-main.92/) and
[TweepFake](https://github.com/tizfa/tweepfake_deepfake_text_detection) are useful for evaluation
design, but TweepFake contains older generators and does not represent current LLM output.

[RAID](https://github.com/liamdugan/raid) and a
[NAACL 2025 evaluation](https://aclanthology.org/2025.findings-naacl.271/) show why headline
accuracy is insufficient. Detectors lose performance on unseen models and ordinary edits; at a
fixed 1% false-positive rate, some tested conditions had no useful true-positive rate.

For this extension:

- phrase, punctuation, structure, and vocabulary signals stay weak and capped;
- content-only evidence cannot produce a red account score;
- short, non-text, and unsupported-language posts should abstain;
- model-heavy methods such as Fast-DetectGPT or Binoculars remain offline comparisons, not
  extension dependencies.

### Repetition is cheap and directly relevant

Exact duplicate replies and lightly edited templates do not prove AI use, but they directly
measure behavior the product is meant to expose. The local implementation can use:

- a normalized exact-text hash;
- a 64-bit SimHash over character n-grams for near duplicates;
- repeated link domains, mention targets, hashtags, and media patterns;
- conversation IDs or parent-post links to distinguish repetition within one thread from the
  same reply sent across unrelated conversations.

Near-duplicate comparison should begin within the same account. Comparing every account against
every other account would cost more and create false alarms from headlines, quotations, memes,
and common short replies.

### Behavior becomes useful over several observations

[BLOC](https://link.springer.com/article/10.1140/epjds/s13688-023-00410-9) represents social
activity as compact sequences of actions, content types, pauses, and repetitions. This is a good
design reference because it makes account behavior incremental instead of requiring a large
language model. [TwiBot-22](https://github.com/LuoUndergradXJTU/TwiBot-22) combines profile,
content, relations, and graph data, but its full social graph is unavailable to a local extension.

Useful local behavior includes:

- repeated or near-duplicate replies in different conversations;
- a high share of generic replies with little relation to visible parent posts;
- repeated link destinations or mention targets;
- unusually regular intervals or bursts, only after enough timestamps and elapsed time;
- a sudden sustained change from the account's earlier observed pattern;
- several accounts posting similar material close together, as a later coordination experiment.

The extension sees a sample of the timeline, not the account's complete activity. Eight posts
encountered over three weeks are eight observations, not a measured three-week posting rate.
Time features must use post timestamps where available and must explain their sampling limits.

### Profile context changes priors, not verdicts

When the user naturally opens an X profile card, the rendered card may provide follower and
following counts, follow relationship, visible common follows, verification, bio, and links. A
profile page may also show join date and post count. Missing fields must stay missing; they are
not negative evidence.

Profile signals should have small, capped effects:

- an established relationship or several common follows can lower suspicion slightly;
- account age can improve identity confidence but does not prove human control;
- extreme follower ratios, no bio, or verification cannot independently raise an account to red;
- localized counts such as `219.9K` and `219,9 k` need tested parsing and a raw `unknown` fallback.

The extension must not synthesize a hover, open a profile, scroll a profile, or make a request to
obtain these fields. It only records fields the user caused X to render during normal browsing.

### Human-compatible evidence matters too

A detector that only accumulates suspicious features will drift upward for every account it sees.
The model also needs evidence that observed behavior is compatible with a person. This is not the
same as proving that a person wrote every post. Human-controlled accounts can schedule posts,
people can use writing tools, and automated accounts can deliberately imitate mistakes.

Separate three concepts:

| Observation | Correct interpretation | Incorrect interpretation |
| --- | --- | --- |
| One-word, fragmentary, or very short post | Insufficient text for authorship scoring | Proof of a human author |
| Original-looking image, video, or voice | Text scoring is not applicable; may support account continuity later | Media means the account is human |
| Typo, correction, slang, or irregular punctuation | Weak human-compatible style evidence | Models or scammers cannot imitate mistakes |
| Varied replies tied closely to different parents | Counterevidence against templated reply automation | The whole account is verified human |
| Reciprocal, context-specific conversation over time | Counterevidence against simple broadcast automation | No automation or AI assistance exists |
| Irregular sessions with ordinary pauses | Counterevidence against rigid scheduling, given enough observations | Irregular timing proves human control |
| Established relationship with the user | A trust prior that can reduce warning severity | Authorship proof |

The strongest locally observable human-compatible signals are longitudinal rather than cosmetic:

- replies contain details specific to the visible parent and change naturally across topics;
- an account participates in back-and-forth conversations rather than only broadcasting;
- vocabulary, length, punctuation, media, and action types vary without repeating a fixed template;
- later posts refer coherently to earlier events or conversations observed from the same account;
- activity appears in bounded sessions with varied gaps rather than an uninterrupted regular
  cadence;
- the account corrects, clarifies, or follows up on an earlier post in context.

Even these are counterevidence, not identity proof. Research on bot and human activity finds
different session dynamics while also noting that newer bots reproduce some short-term human
patterns. See [Measuring bot and human behavioral dynamics](https://arxiv.org/abs/1802.04286).
Human-AI mixtures make binary labels weaker still: an
[ACL 2025 evaluation of AI-polished writing](https://aclanthology.org/2025.findings-acl.1303/)
found that detectors often flag even lightly polished human text.

Typos need special care. Deliberate perturbations, paraphrasing, and changed generation settings
can defeat detectors. The
[NAACL practical evaluation](https://aclanthology.org/2025.findings-naacl.271/) demonstrates
evasion under moderate attacks, while a
[2025 sampling study](https://aclanthology.org/2025.findings-emnlp.609/) finds that small decoding
changes can sharply alter detector performance. A spelling error should therefore reduce a
style-only signal slightly at most. It should never cancel behavioral evidence.

Counterevidence must apply to the family it actually contradicts:

- varied, parent-specific replies reduce repetition and conversation suspicion;
- varied session timing reduces temporal suspicion;
- an established relationship lowers the account-context prior;
- spelling errors only affect content-style evidence;
- media presence usually changes coverage rather than suspicion.

Do not sum all “human points” into a universal negative score. That would let a bot add typos or
images to erase unrelated automation evidence. Keep raising and lowering evidence inside each
family, cap lowering effects, then combine the remaining family scores.

## Local evolving account model

### State ownership

Use extension `browser.storage.local`, not page `window.localStorage`. Chrome documents that
content-script web storage is shared with the host page, cannot be used by service workers, and
can disappear with browsing-data deletion. Extension storage is asynchronous, shared by
extension contexts, and has a 10 MB default local quota. See the
[Chrome storage API](https://developer.chrome.com/docs/extensions/reference/api/storage) and
[Firefox `storage.local`](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/storage/local).

The background service worker should own persisted state. Content scripts extract a sanitized
observation and send it to the worker. This gives one writer across tabs, central deduplication,
schema migrations, batched writes, and a clean boundary if storage later changes.

Use a stable X user ID when an approved source exposes one. A handle is only a temporary key:
handles can change and be reassigned. Until a stable ID exists, keep normalized handle, observed
display-name changes, first and last seen times, and avoid permanent judgments.

### Store bounded features, not an archive

The aim is not to gather as much data as possible. It is to preserve the smallest evidence that
improves the score. Raw post archives add privacy, quota, and policy costs without necessarily
improving detection.

A first schema can look like this:

```ts
type AccountEvidenceV1 = {
  schemaVersion: 1;
  accountKey: string;
  handle: string;
  firstSeenAt: number;
  lastSeenAt: number;
  observationCount: number;
  recentPosts: PostSignatureV1[]; // capped, for example 50 posts or 30 days
  aggregates: AccountAggregatesV1;
  profile?: ProfileSnapshotV1;
  userLabels: UserLabelV1[];
};

type PostSignatureV1 = {
  postId?: string;
  conversationId?: string;
  observedAt: number;
  publishedAt?: number;
  kind: 'post' | 'reply' | 'quote' | 'repost' | 'unknown';
  language?: string;
  textLength: number;
  exactHash?: string;
  simHash?: string;
  linkDomains: string[];
  mentionCount: number;
  contentScore: number;
  contentReasons: string[];
  contentCounterevidence: string[];
};
```

`AccountAggregatesV1` should contain counters and small histograms: post-kind counts, active-hour
bins, inter-post gap bins, unique conversations, duplicate counts, link-domain frequency, and
online mean and variance for text length. Welford's algorithm updates mean and variance without
retaining every value.

Do not store full post text by default. Exact hashes and SimHash support repetition checks. A
short rolling raw-text buffer may exist only in an explicit diagnostics mode with a clear delete
control. Cap each account record, expire old signatures, and expose total storage usage.

### Incremental processing

For each newly rendered post:

1. Extract a typed observation and reject duplicates by post ID or a session key.
2. Compute content features once.
3. Load the account record through the background worker's memory cache.
4. Compare the signature with only that account's bounded recent signatures.
5. Update aggregate counters in constant time.
6. Recompute suspicion, coverage, reasons, and color.
7. Queue one batched storage write instead of writing on every DOM mutation.

This keeps normal work close to O(1) per post. Near-duplicate matching is O(k), where `k` is a
small fixed history cap. No model inference, full-history scan, or cross-account matrix is needed
for the first version.

Profile-card observations use the same path. A timestamped `ProfileSnapshotV1` replaces the old
snapshot only after parsing succeeds. It never overwrites known values with missing DOM fields.

### Evidence families and score gates

Keep family subscores rather than one unexplained formula:

| Family | Example evidence | Initial maximum influence |
| --- | --- | --- |
| Content | phrase/style rules on observed posts | Low |
| Repetition | same template across unrelated conversations | High |
| Temporal | repeated regular gaps or sustained bursts | Medium |
| Conversation | generic or mismatched replies to visible parents | Medium |
| Account context | age, follower/following, profile completeness | Low |
| Relationship | user follows account, common follows | Low and mostly downward |

Each family should contain both suspicion and counterevidence. For example, the conversation
family may contain repeated generic replies as raising evidence and varied parent-specific
answers as lowering evidence. Lowering evidence can bring its own family toward zero, but should
not erase an independent family.

Initial rules should be deterministic and inspectable. Do not call the number a probability
until it has been calibrated on labeled data.

- `unknown`: too little eligible evidence, regardless of the raw point total.
- `low`: enough coverage with no strong automation evidence.
- `medium`: one strong behavioral signal or independent medium signals.
- `high`: strong evidence from at least two independent families, including one behavioral
  family. Content and profile metadata alone cannot qualify.

No local observation should produce a “confirmed human” state. Green remains “low suspicion from
the evidence observed,” with coverage and the strongest counterevidence shown alongside the
observation count.

Coverage should consider eligible post count, distinct conversations, observed time span,
profile availability, and family count. Suggested starting gates, to be tested rather than
treated as facts:

- repetition activates after 3 comparable posts;
- temporal features activate after 8 timestamped posts spanning at least 6 hours;
- low suspicion needs at least 5 posts from 2 conversations;
- high suspicion needs 2 evidence families and at least 5 eligible observations.

This is how the score can remain strict without becoming reckless: amber catches concerning
patterns, while red has a high evidence bar. The tooltip should say, for example, “Medium
suspicion: 4 near-duplicate replies across 3 conversations; based on 9 observed posts.”

### Decay, identity changes, and feedback

Evidence should decay. Old behavior must not become a permanent label. Expire individual post
signatures after a fixed window and reduce aggregate influence over a longer window. Large
changes in handle, display name, bio, and posting style should lower identity continuity and can
start a new observation epoch.

User feedback is valuable but must remain separate from inferred evidence. “Likely automated,”
“useful account,” and “wrong signal” are local labels. Blocking or muting is not ground truth for
AI use. Feedback can tune the user's display thresholds later without silently rewriting the
shared detector.

## Evaluation before tuning

Build a reviewed, lawful X-like test set before adding many rules. Labels should distinguish
human, generated, human-edited AI, repetitive automation, and unknown. Split by author,
conversation, time, and generator so duplicates cannot leak across training and testing.

Report false-positive rate first:

- true-positive rate at 0.1% and 1% false-positive rates;
- precision under plausible prevalence;
- abstention rate and coverage;
- results by language and length;
- account-level results as observations accumulate from 1, 3, 5, 10, and 20 posts;
- audits of quotations, memes, brands, support accounts, scheduled posts, non-native writing,
  one-word posts, media posts, spelling errors, and people who reuse their own phrasing;
- adversarial tests where automated posts add typos, slang, irregular delays, or media to imitate
  human-compatible features;
- ablation results showing whether each counterevidence rule reduces false positives without
  hiding repeated automation.

Replay observations in chronological order. The test must show both whether the final account
score is correct and whether it becomes overconfident too early.

The most useful repositories are:

| Project | Use here |
| --- | --- |
| [BLOC](https://link.springer.com/article/10.1140/epjds/s13688-023-00410-9) | Compact incremental behavior representation |
| [TwiBot-22](https://github.com/LuoUndergradXJTU/TwiBot-22) | Profile/content/network feature taxonomy and evaluation warnings |
| [TweepFake](https://github.com/tizfa/tweepfake_deepfake_text_detection) | Tweet preprocessing and author-aware splits, not current labels |
| [RAID](https://github.com/liamdugan/raid) | Fixed-false-positive evaluation and adversarial testing |

Read repository licenses and dataset terms before copying code or data.

## Policy and account-safety boundary

X's current terms say that crawling or scraping the service without prior written consent is
prohibited. See the [X Terms of Service](https://x.com/en/tos), effective April 10, 2026 outside
the EU/EFTA/UK, with separate regional terms on the same page. This document is engineering
guidance, not a legal conclusion.

The lowest-risk product boundary is:

- process only posts and profile details already rendered through the user's normal actions;
- do not cause navigation, hovering, scrolling, or requests to collect more data;
- do not access hidden or private X endpoints;
- do not export raw X content or build a background crawler;
- do not perform account actions;
- review the applicable X terms and obtain policy or legal advice before release.

An official X API integration would be a separate opt-in feature with its own authentication,
billing, caching, retention, and Developer Agreement review.

## Path to shared learning

Two future products must not be confused.

### Shared model improvement

Users could explicitly opt in to contribute versioned derived features and deliberate labels.
Raw text and handles should be excluded by default. A hash of a public handle is not anonymous;
it can be guessed from the public handle list.

The server would need schema validation, duplicate control, rate limits, poisoning resistance,
independent review data, model versioning, rollback, and deletion handling. The extension would
download a signed data or model artifact and score locally. Manifest V3 requires executable code
to be bundled with the extension, so downloaded rules must remain data interpreted by shipped
code rather than remote JavaScript or WASM. See Chrome's
[remote-hosted-code policy](https://developer.chrome.com/docs/extensions/develop/migrate/remote-hosted-code).

### Shared account reputation

A common list keyed by account is more sensitive than anonymous model training. It creates a
reputation system and needs stable account IDs, several independent reporters, evidence expiry,
ownership-change handling, anti-brigading controls, moderation, correction, and appeal paths.
It also requires permission to collect and redistribute the relevant X data.

Do not build this into the first scoring schema. Version the local observation and label types so
an approved export can be added later, but keep networking absent and contribution off by
default.

## Recommended build order

1. Freeze the current content scorer as the weak baseline.
2. Add typed observations, background-owned storage, retention, and deletion.
3. Add exact and near-duplicate evidence within each account.
4. Add chronological replay tests and coverage gates.
5. Record user-opened profile context with capped influence.
6. Add temporal and conversation features only after enough samples exist.
7. Calibrate thresholds on false positives before considering any trained model or shared data.

The first useful algorithm is a conservative incremental evidence combiner. It should become
more informed over time, not merely more certain.
